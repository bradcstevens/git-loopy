# Research: Web stacks that fit the Python Runner's packaging

> Wayfinder research ticket: [#656: Research web stacks that fit the Python Runner's packaging](https://github.com/bradcstevens/git-loopy/issues/656)
> Researched 2026-09-25 (America/Denver). The corporate-feed snapshot and upstream releases can change.
> **No pick.** This file lists constraints for "Decide the web frontend's launch parameter and lifecycle" and "Prototype the web board and card drawer".

## Question

Which web server and client options fit git-loopy's Python distribution and this environment's constraints, and how does a Run's Event stream reach a browser? The destination calls for a board, card drawer, settings and live activity ([map #648](https://github.com/bradcstevens/git-loopy/issues/648), [Hermes UI reference](wanderloots-hermes-coordination/hermes-ui-reference.md)); this research does not choose a stack or a launch parameter.

## How facts were gathered

- **Primary docs** were read directly: python.org, aiohttp, starlette.dev, uvicorn.dev, fastapi.tiangolo.com, htmx.org / four.htmx.org, vite.dev, react.dev, preactjs.com, WHATWG HTML, MDN, RFC Editor, OWASP, Jupyter Server, docs.brew.sh, hatch.pypa.io, docs.npmjs.com. Source files were read with `gh api` from GitHub.
- **Python package metadata** came only from the corporate simple index `https://packagefeedproxy.microsoft.io/pypi/simple/<name>/`, using the PEP 691 JSON form (`Accept: application/vnd.pypi.simple.v1+json`). The feed does not expose PEP 658 `core-metadata` for these files. To get `Requires-Dist`, the wheel was downloaded into memory from the feed's own file URLs and its `METADATA` was parsed. Those URLs are on `ms-feed-25.pkgs.visualstudio.com` and redirect (303) to `*.vsblob.vsassets.io`, which is Azure DevOps Artifacts storage. Nothing was installed and nothing was written to disk.
- **npm metadata** came only from `npm view` against the configured registry `https://packagefeedproxy.microsoft.io/npm/`, as reported by `npm config get registry`.
- **Dependency counts** are estimates from a naive transitive walk, not a real resolver. Each dependency is taken at the newest stable version on the feed. Environment markers are evaluated for CPython 3.11 on two platforms: Windows AMD64 and macOS arm64. Extras are off unless the table names them, and the root package is not counted. Both package membership and exact versions can differ in a valid resolution of this Runner's existing constraints; for example, pydantic pins an exact pydantic-core.
- No public registries, mirrors or release assets were contacted.

## Bottom line

- **Distribution boundary:** the Python Runner's Hatch wheel declares Rich 13 and Textual `<6`; web dependencies can be added there or in an extra, but the current Homebrew and winget channels install only the **Rust helper archive**, not the Python wheel. Homebrew-core Python-resource rules therefore do *not* describe this project's tap ([`pyproject.toml:24-72`](../../git-loopy/python/pyproject.toml), [`homebrew.py:275-320`](../../git-loopy/python/git_loopy/homebrew.py), [`windows_channels.py:537-558`](../../git-loopy/python/git_loopy/windows_channels.py), [release channels](../releases/README.md#package-channels)).
- **Server weight:** stdlib needs no new packages but leaves SSE framing and HTTP hardening to the app ([Python `http.server`](https://docs.python.org/3/library/http.server.html)); aiohttp includes streaming and WebSockets but has compiled wheels ([aiohttp docs](https://docs.aiohttp.org/en/stable/web_quickstart.html), §7); Starlette plus minimal Uvicorn has a small pure-wheel closure, but WebSocket support needs a separately installed protocol package ([Starlette responses](https://starlette.dev/responses/), [Uvicorn installation](https://uvicorn.dev/installation/), §7).
- **FastAPI vs Textual:** FastAPI has built-in SSE but adds compiled `pydantic-core` ([FastAPI SSE](https://fastapi.tiangolo.com/tutorial/server-sent-events/), §7); textual-serve reuses the existing Textual/Rich stack but serves a Textual app over WebSocket rather than custom HTML for a board ([textual-serve](https://github.com/Textualize/textual-serve), [`pyproject.toml:28-34`](../../git-loopy/python/pyproject.toml)).
- **Client trade-off:** plain templates or a vendored htmx file avoid a release-time Node build ([htmx](https://htmx.org/)); a Vite-built React/Preact SPA can ship as wheel assets but needs a reproducible corporate-feed npm build and a Node version compatible with Vite ([Vite guide](https://vite.dev/guide/), [Hatch build config](https://hatch.pypa.io/latest/config/build/)).
- **Streaming seam:** the detached worker flushes scrubbed JSONL; the current parent follows the trace by file seek position, not a network protocol. A browser needs a separate server that reads an explicitly selected Run's trace, replays then follows it, and maps the lines to SSE or WebSocket; the Event envelope has no sequence number ([`persist.py:358-401`](../../git-loopy/python/git_loopy/persist.py), [`run_sidecar.py:371-435`](../../git-loopy/python/git_loopy/run_sidecar.py), [`wrapper-contract.md:672-690`](../wrapper-contract.md)).
- **Transport trade-off:** SSE has browser-native reconnection but needs an application cursor for reliable file replay; `EventSource` cannot set custom auth headers and HTTP/1.1 has a six-connections-per-origin browser limit. WebSocket is bidirectional but needs application-managed replay and explicit Origin checks ([WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html), [MDN](https://developer.mozilla.org/en-US/docs/Web/API/EventSource), [RFC 6455 §10.2](https://www.rfc-editor.org/rfc/rfc6455#section-10.2)).
- **Security:** loopback binding alone does not address DNS rebinding or cross-site requests: validate Host and Origin, require token authentication and CSRF protections for mutating routes, and authenticate WebSocket handshakes ([Jupyter security](https://jupyter-server.readthedocs.io/en/latest/operators/security.html), [OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html), [OWASP WebSocket](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html)).
- **Delivery gaps:** ADR-0058 *specifies* `attach` and `stop`, but today's CLI only dispatches `runs`; Windows helper attachment is also a known gap, so a browser must not assume these commands work already ([ADR-0058](../adr/0058-init-precedes-the-run-and-clients-do-not-own-its-lifetime.md), [`cli.py:3197-3231`](../../git-loopy/python/git_loopy/cli.py), [release helper gap](../releases/README.md#the-downloadable-helper-baseline)).
- **Corporate feed snapshot:** queried candidate packages are present, but the corporate feeds lacked upstream Starlette 1.7.0, Uvicorn 0.54.0 and Vite 8.3.1; htmx's feed `latest` tag disagreed with the upstream statement. Those specific versions are unavailable here, not a reason to bypass the feeds (§7; [Starlette releases](https://starlette.dev/release-notes/), [Uvicorn releases](https://uvicorn.dev/release-notes/), [htmx](https://htmx.org/)).

### 1.2 Notes per option

- **stdlib:**
  - Use `ThreadingHTTPServer`, which exists "to handle web browsers pre-opening sockets, on which HTTPServer would wait indefinitely" (added in 3.7) ([http.server](https://docs.python.org/3/library/http.server.html)).
  - `ThreadingMixIn.daemon_threads` defaults to `False`, which means "Python will not exit until all threads created by ThreadingMixIn have exited". This matters for long-lived SSE handlers at shutdown ([socketserver](https://docs.python.org/3/library/socketserver.html)).
  - With `protocol_version='HTTP/1.1'`, the docs require accurate `Content-Length` in responses ([http.server](https://docs.python.org/3/library/http.server.html)). An open-ended SSE stream therefore needs HTTP framing designed and tested separately; default HTTP/1.0 connection-close behavior is one possibility, not a tested implementation.
- **aiohttp:**
  - `handler_cancellation` cancels the handler task when the client disconnects ([web_advanced](https://docs.aiohttp.org/en/stable/web_advanced.html)).
  - Graceful shutdown closes idle keep-alive connections and fires `on_shutdown` ([web_advanced](https://docs.aiohttp.org/en/stable/web_advanced.html)). This is relevant to closing long-lived SSE/WS connections.
  - `port=0` lets the OS choose a free port ([web_reference](https://docs.aiohttp.org/en/stable/web_reference.html)).
- **Starlette:**
  - Reached 1.0.0 on 2026-03-22. 1.7.0 (2026-09-23) "requires AnyIO 4" and adds "IPv6 hosts in TrustedHostMiddleware" ([release notes](https://starlette.dev/release-notes/)).
  - `TrustedHostMiddleware` "Enforces that all incoming requests have a correctly set Host header, in order to guard against HTTP Host Header attacks", and supports `allowed_hosts=["[::1]"]` ([middleware](https://starlette.dev/middleware/)).
  - `CORSMiddleware` has an `allow_private_network` flag for Private Network Access preflights ([middleware](https://starlette.dev/middleware/)).
- **textual-serve:**
  - The browser WebSocket handler calls `websocket.prepare(request)` with no Origin or token check in the code path shown (`Textualize/textual-serve:src/textual_serve/server.py:310-330` @ `fa5cf5f`).
  - The subprocess is started with `asyncio.create_subprocess_shell` and `TEXTUAL_DRIVER=textual.drivers.web_driver:WebDriver` (`src/textual_serve/app_service.py:73-99` @ `fa5cf5f`).
  - The README states that the custom protocol "does not simply expose a shell" ([README](https://github.com/Textualize/textual-serve)).
  - This Runner already requires `rich>=13.7,<14` and `textual>=0.86,<6`; the feed's latest Textual 8.2.8 and Rich 15.0.0 are *not* compatible with those caps. The 21-package latest-version closure is therefore **not** the incremental dependency cost of installing textual-serve into this Runner; resolving its compatible version and incremental package set remains open ([`pyproject.toml:28-34`](../../git-loopy/python/pyproject.toml), §7).

### 3.2 Cost of an npm build at release, given the corporate feeds

- **Lockfile URLs.** package-lock `resolved` records "the place where the package was actually resolved from", which is a tarball URL for registry packages ([package-lock.json](https://docs.npmjs.com/cli/v11/configuring-npm/package-lock-json)). The npm config `replace-registry-host` defaults to `"npmjs"`, which rewrites lockfile URLs from the default public registry to the configured registry. `omit-lockfile-registry-resolved` writes lockfiles without `resolved` keys ([npm config](https://docs.npmjs.com/cli/v11/using-npm/config)).
  - *Implication, not tested here:* inspect lockfile `resolved` fields and npm config before trusting a build on another runner; public or corporate hostnames may be embedded, and this Mac must use only its configured corporate feed. A different CI runner's feed access is unknown.
- **Frozen installs.** `npm ci` requires an existing lockfile, errors instead of updating it on mismatch, and "will never write to package.json or any of the package-locks" ([npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci)).
- **Supply-chain controls.** `min-release-age` and `before` limit which versions can be installed by publish date. `ignore-scripts` turns off lifecycle scripts ([npm config](https://docs.npmjs.com/cli/v11/using-npm/config)).
- **Native binaries.** Every build platform needs its matching optional binary. The feed has `@rolldown/binding-darwin-arm64`, `-win32-x64-msvc` and `-linux-x64-gnu` @1.2.9; `lightningcss-darwin-arm64`, `-win32-x64-msvc` and `-linux-x64-gnu` @1.33.0; and `fsevents` @2.3.3 (§7.2).
- **Python sdist/editable builds:** if assets exist only in a direct wheel build, builds from sdist and editable installs need an explicit strategy for finding or producing them ([Hatch build config](https://hatch.pypa.io/latest/config/build/), [local Hatch packaging proof](verify-hatchling-force-include.md)).
- **This repository's current channels do not build the Python sdist.** Homebrew and winget deliver a prebuilt Rust helper, so a proposed web-enabled Python wheel needs its own release/install story; a Node release build is not automatically run by either package channel ([`homebrew.py:275-320`](../../git-loopy/python/git_loopy/homebrew.py), [`windows_channels.py:537-558`](../../git-loopy/python/git_loopy/windows_channels.py), [release channels](../releases/README.md#package-channels)).

## 4. Streaming Events to a browser: SSE vs WebSocket

| Property | SSE (`text/event-stream`) | WebSocket |
|---|---|---|
| Direction | Server to client only. The htmx SSE docs say: "SSE is a uni-directional service" ([htmx SSE ext](https://htmx.org/extensions/sse/)). | Two-way ([RFC 6455](https://www.rfc-editor.org/rfc/rfc6455)) |
| Resume after disconnect | Built in: the client keeps a **last event ID** and a **reconnection time**, and sends a `Last-Event-ID` header when it reconnects ([WHATWG HTML §9.2](https://html.spec.whatwg.org/multipage/server-sent-events.html)). FastAPI documents reading `Last-Event-ID` to resume ([FastAPI SSE](https://fastapi.tiangolo.com/tutorial/server-sent-events/)). | None built in; the application designs its own |
| Browser API limits | `new EventSource(url, { withCredentials })` is the only option ([WHATWG](https://html.spec.whatwg.org/multipage/server-sent-events.html), [MDN EventSource()](https://developer.mozilla.org/en-US/docs/Web/API/EventSource/EventSource)), so **no custom headers**. htmx 4's fetch-based SSE avoids this ([hx-sse](https://four.htmx.org/extensions/hx-sse)). | The constructor takes `url` and `protocols` only ([MDN WebSocket()](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/WebSocket)), so there are no custom headers either. The `WebSocket` interface "doesn't support backpressure", while `WebSocketStream` does ([MDN WebSockets API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)). |
| Connection cap | "When not used over HTTP/2, SSE suffers from a limitation to the maximum number of open connections … (6) … per browser + domain", marked "Won't fix" in Chrome and Firefox ([MDN EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource)). WHATWG suggests sharing one `EventSource` through a shared worker ([WHATWG §9.2.7](https://html.spec.whatwg.org/multipage/server-sent-events.html)). No server option here offers HTTP/2 over cleartext loopback by default. Uvicorn's `--http2` needs the experimental `zttp` ([settings](https://uvicorn.dev/settings/)). | Not researched: whether WebSocket connections count against the same per-host pool is unknown |
| Keep-alive | Send a comment line "every 15 seconds or so" to survive proxies ([WHATWG §9.2.7](https://html.spec.whatwg.org/multipage/server-sent-events.html)) | Ping/pong frames ([RFC 6455](https://www.rfc-editor.org/rfc/rfc6455)). aiohttp offers `WebSocketResponse(heartbeat=…)`, which textual-serve uses with 15 (`server.py:321`). |
| Server support (§1) | stdlib (manual), aiohttp `StreamResponse`/`aiohttp-sse`, Starlette `StreamingResponse`/`sse-starlette`, FastAPI `fastapi.sse` (sources in §1) | aiohttp (built in), Starlette + a WS-capable ASGI server. The stdlib has none (sources in §1). |
| Security | An authenticated read-only GET still needs Host validation and protection against unauthorized reads; mutating requests need CSRF defenses (§5; [OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)). | "Servers … SHOULD verify the \|Origin\| field", and reject with 403 ([RFC 6455 §10.2](https://www.rfc-editor.org/rfc/rfc6455#section-10.2)). "This protocol doesn't prescribe any particular way that servers can authenticate clients" ([§10.5](https://www.rfc-editor.org/rfc/rfc6455#section-10.5)). Browsers send cookies on the handshake, which leads to CSWSH ([OWASP WebSocket CS](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html)). |

### Actual Runner-to-browser seam

- A TTY launch creates one Run ID and writers, starts `python -m git_loopy.run_child` in a detached process, then runs the terminal client in the parent. The child drives the line printer independently; there is **no existing browser transport, Event socket or HTTP server** in this path ([`cli.py:3574-3615`](../../git-loopy/python/git_loopy/cli.py), [`run_sidecar.py:320-347`](../../git-loopy/python/git_loopy/run_sidecar.py), [`run_child.py:1-42`](../../git-loopy/python/git_loopy/run_child.py)). ADR-0058 says clients only observe, do not own the worker, and only Stop controls it ([ADR-0058, "Clients observe"](../adr/0058-init-precedes-the-run-and-clients-do-not-own-its-lifetime.md#clients-observe-only-stop-controls-the-run)).
- The worker's `EventEmitter` scrubs and writes replay-grade Events before fan-out. `EventLogWriter` appends and flushes each JSONL line to `.git-loopy/logs/<iso>-<run_id>.jsonl`; the envelope is `ts`, `run_id`, `iter`, `type` and sorted payload, with no per-record sequence or browser cursor ([`emit.py:94-110`](../../git-loopy/python/git_loopy/emit.py), [`persist.py:1-29,358-401`](../../git-loopy/python/git_loopy/persist.py), [`wrapper-contract.md:672-690`](../wrapper-contract.md)). Timestamp and iteration alone are not a lossless resume position; assigning a byte-offset cursor to each **complete** line is one possible design, not implemented today ([`run_sidecar.py:371-419`](../../git-loopy/python/git_loopy/run_sidecar.py), [WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html)).
- `TraceFollower.poll()` tracks a text-file seek cookie with `TextIOWrapper.tell()`, buffers incomplete lines, and treats `wrapper.run.end` or loss of the lock-proven live owner as completion. The parent renders complete lines; the Rust helper receives trace and control paths, not a network address. A web server could adopt the same trace-following semantics, including not treating temporary EOF as a finished Run, but needs its own per-client replay cursors, Run scoping, permissions, disconnect handling, and a position-to-SSE-ID or WebSocket-resume mapping; the text-file seek cookie is not itself a portable byte offset or authenticated browser cursor ([`run_sidecar.py:371-485,487-510`](../../git-loopy/python/git_loopy/run_sidecar.py), [`run_control.py:1-60`](../../git-loopy/python/git_loopy/run_control.py), [Python text I/O](https://docs.python.org/3/library/io.html#io.TextIOBase.tell), [WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html)).
- `git-loopy runs` already lists this clone's registered worktrees and their explicit Run identities; discovery provides trace and control paths with `live`, `dead` or `unknown` liveness and refuses to infer a target. ADR-0058 requires `git-loopy attach <run-id>` and `git-loopy stop <run-id>`, but neither is dispatched by the present CLI: do **not** treat them as implemented endpoints. A read-only browser can use a GET stream plus separate authenticated POSTs *if* control routes are later implemented; WebSocket is not required merely to display live activity ([`runscmd.py:1-52`](../../git-loopy/python/git_loopy/runscmd.py), [`run_discovery.py:1-73,128-176`](../../git-loopy/python/git_loopy/run_discovery.py), [`cli.py:3197-3231`](../../git-loopy/python/git_loopy/cli.py), [ADR-0058](../adr/0058-init-precedes-the-run-and-clients-do-not-own-its-lifetime.md)).
- The Event schema explicitly allows unknown event types/payload fields and records only final scrubbed replay Events for SDK message deltas; the board, card drawer, settings and live activity may need new Event producers or separate read APIs rather than assuming every displayed datum is in the current trace ([`wrapper-contract.md:672-706`](../wrapper-contract.md), [`emit.py:1-43`](../../git-loopy/python/git_loopy/emit.py), [Hermes UI reference](wanderloots-hermes-coordination/hermes-ui-reference.md)).

## 5. Local-server security basics

| Threat | What primary sources say | Source |
|---|---|---|
| **Exposure beyond the machine** | The MCP transport spec says local servers "SHOULD bind only to localhost (127.0.0.1) rather than all network interfaces (0.0.0.0)". The defaults vary: aiohttp `run_app` uses `'0.0.0.0'`, Uvicorn `'127.0.0.1'`, textual-serve `"localhost"`, and Jupyter `ServerApp.ip` `'localhost'`. | [MCP transports](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports), [aiohttp](https://docs.aiohttp.org/en/stable/web_reference.html), [uvicorn](https://uvicorn.dev/settings/), [textual-serve](https://github.com/Textualize/textual-serve), [Jupyter config](https://jupyter-server.readthedocs.io/en/latest/other/full-config.html) |
| **DNS rebinding** | "Through DNS rebinding, an attacker can temporarily control the origin for their requests so that they seem to originate from a local IP address" (Node.js). MCP: servers "MUST validate the Origin header on all incoming connections to prevent DNS rebinding attacks". Jupyter's `allow_remote_access=False` gives a 403 when the `Host` header is non-local. Only loopback IPs and `local_hostnames` (default `['localhost']`) are allowed. Starlette `TrustedHostMiddleware` does the same kind of Host check. | [Node.js security](https://nodejs.org/en/learn/getting-started/security-best-practices), [MCP](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports), [Jupyter config](https://jupyter-server.readthedocs.io/en/latest/other/full-config.html), [Starlette middleware](https://starlette.dev/middleware/) |
| **CSRF** | OWASP recommends: Fetch Metadata `Sec-Fetch-Site` ("supported in all major browsers since March 2023", with a mandatory fallback to Origin/Referer checks); custom request headers for AJAX, where "No token is needed"; synchronizer tokens; and SameSite cookies. For the Origin check, match the entire origin, so that `example.org.attacker.com` does not pass. | [OWASP CSRF CS](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) |
| **Cross-site WebSocket hijacking** | Validate Origin on every handshake against an explicit allowlist, not substring matching. Put CSRF tokens in handshakes. Use SameSite cookies. | [OWASP WebSocket CS](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html), [RFC 6455 §10.2](https://www.rfc-editor.org/rfc/rfc6455#section-10.2) |
| **Token authentication (Jupyter model)** | Token authentication is "on by default". The token can be sent in `Authorization: token …`, as a `?token=` URL parameter, or through the login form. It is logged to the terminal. Jupyter also writes a local `file://…/jpserver-<pid>-open.html` that redirects with the token. After login, a cookie means "you won't need to use the token again". Disabling authentication is "NOT RECOMMENDED". XSRF protection requires API requests to either come from served pages (XSRF cookie + token) or authenticate with a token. | [Jupyter security](https://jupyter-server.readthedocs.io/en/latest/operators/security.html), [Jupyter config (`disable_check_xsrf`)](https://jupyter-server.readthedocs.io/en/latest/other/full-config.html) |
| **Browser mitigations (not relied on)** | Chrome's Local Network Access gates requests from public sites to local and **loopback** destinations behind a permission prompt. It was opt-in testing in Chrome 138 and replaces the paused Private Network Access effort. | [Chrome LNA blog](https://developer.chrome.com/blog/local-network-access) |

**Transport-specific consequences** (inferred from the rows above):
- `EventSource` cannot send an `Authorization` header, so an SSE token has to come from a cookie set after a token exchange or from a URL query parameter. htmx 4's fetch-based SSE can send headers.
- A browser WebSocket cannot supply a custom `Authorization` header; an authenticated handshake needs an accepted cookie, URL or subprotocol token scheme. A token sent only in the first message must not grant access before that message is verified ([MDN WebSocket()](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/WebSocket), [OWASP WebSocket](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html)).
- A URL token can leak through history and logs. Jupyter's `file://` redirect page is one existing way to avoid printing a bare token, although Jupyter does also print the token.

## 6. Windows support and build/distribution facts

### 6.1 Windows

- **asyncio on Windows:**
  - `ProactorEventLoop` is the default and supports subprocesses. `SelectorEventLoop` does not, and is limited to 512 sockets.
  - All Windows loops lack `add_signal_handler`/`remove_signal_handler` and `AF_UNIX` servers.
  - Monotonic clock resolution is about 15.6 ms.

  Source: [asyncio-platforms](https://docs.python.org/3/library/asyncio-platforms.html).
- **uvloop** is not available on Windows ([uvicorn settings](https://uvicorn.dev/settings/)). The feed has no Windows wheels for uvloop 0.22.1 (§7.1).
- **Unix-socket binding:** aiohttp `path=` and Uvicorn `--uds` bind to Unix domain sockets ([aiohttp](https://docs.aiohttp.org/en/stable/web_reference.html), [uvicorn](https://uvicorn.dev/settings/)). Neither is available on Windows, per the asyncio limits above.
- **textual-serve on Windows:** see §1.1 (issues #4 and #38).

### 6.2 Packaging and distribution

- **Hatch:**
  - `artifacts` includes "files that are ignored by your VCS, such as those that might be created by build hooks" ([Hatch build config](https://hatch.pypa.io/latest/config/build/)).
  - `force-include` maps arbitrary paths into the distribution ([same page](https://hatch.pypa.io/latest/config/build/)).
  - A custom build hook (`hatch_build.py`) can run steps such as a JS build during `build` ([custom build hook](https://hatch.pypa.io/latest/plugins/build-hook/custom/)).
- **Homebrew core Python formulae, *only if a future channel distributes the Python package through Homebrew core*** ([Language-Specific Formulae](https://docs.brew.sh/Language-Specific-Formulae)):
  - "All Python module dependencies and their recursive dependencies that are not provided by another formula must be declared as resources."
  - `brew update-python-resources` generates the resource blocks.
  - `std_pip_args` "delays packages published within Homebrew's release-cooldown period, disables automatic dependency resolution and binary wheels".
  - *Conditional implication:* if a Python-core formula is later adopted, its recursive Python dependencies need resources and its compiled dependencies may be built from sdists. This does **not** apply to the currently published git-loopy tap formula ([`homebrew.py:275-320`](../../git-loopy/python/git_loopy/homebrew.py)).
  - Node formulae use `std_npm_args`, which "applies the package release cooldown" and ignores lifecycle scripts by default (same page).
- **Current Homebrew and winget channels:** the maintained Homebrew *tap* installs the released `git-loopy-tui` executable from a verified platform archive (`bin.install`); winget is `InstallerType: zip`, `NestedInstallerType: portable`, with the same Windows helper executable as its portable alias. Neither channel installs a Python wheel, wheel extras or npm assets today. Stable releases update them by pointing to prebuilt archives; prereleases do not ([`homebrew.py:275-320`](../../git-loopy/python/git_loopy/homebrew.py), [`windows_channels.py:537-558`](../../git-loopy/python/git_loopy/windows_channels.py), [`releases/README.md:433-458`](../releases/README.md)). The published Rust helper's Windows attach/control protocol is still listed as missing ([`releases/README.md:85-93`](../releases/README.md)).
- **Python wheel:** Hatchling currently includes only `git_loopy`, requires Python >=3.11, pins `github-copilot-sdk==1.0.14`, and caps Rich `<14` and Textual `<6`. OTel and release-time YAML parsing live in extras because the base stays light and the runtime never reads YAML. Web dependencies and SPA assets are *not* declared in this manifest; static assets would need packaging in both wheel and any relevant sdist/editable-install path ([`pyproject.toml:1-85`](../../git-loopy/python/pyproject.toml), [Hatch build config](https://hatch.pypa.io/latest/config/build/), [local Hatch packaging proof](verify-hatchling-force-include.md)). The current release documentation calls its downloadable artifacts Rust helpers, not Python wheels ([`releases/README.md:28-48,65-94`](../releases/README.md)).
