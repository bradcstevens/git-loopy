# git-loopy 0.9.0-dev.0

git-loopy 0.9.0-dev.0 is a **prerelease**: a published snapshot of `main` while
0.9.0 is still being built, not the Release that milestone is owed. It is marked
prerelease on GitHub, reaches no package channel, and is not what "the stable
Release" resolves to anywhere.

It exists because the routing work landed in a shape worth installing before it
is finished. Everything below is on `main` and passes the Runner-family
Conformance gate; the eleven issues 0.9.0 still owes are listed at the end, and
none of them are implied by this Release.

The Runner family is unchanged in shape — a Python reference Orchestrator, native
shell and PowerShell Orchestrators, and a Rust Dashboard core, all pinned against
the same Conformance fixtures.

## Per-issue routing gets a table that is actually routable

The shipped `[routing]` table `git-loopy init` writes offered two pairs the
design had already **rejected**, and nothing was checking. `chore` routed to
`claude-haiku-4.5 @ none`, a model whose reasoning-effort roster entry is the
empty set — and an effort supplied to an effort-incapable model *hard-rejects
session creation* rather than downgrading, so that route aborted its Iteration
the moment an issue carried the label. `review` routed to `gpt-5.6-sol`, refused
on the record because the containment argument that admits it holds for a
read-only subagent and not for a `review` Task type, which is a full
write-capable Lane that closes its own issue.

Zero issues carried a `task-type:` label at the time, which is exactly why this
had to be corrected before the corpus was labelled rather than after.

A reasoning-incapable model is now **unroutable** as a contract MUST. That was
already invariant at four separate layers; the shipped table was the one thing
contradicting all four, and the effort gate was quietly rescuing it. A pair that
survives only because something upstream rewrites it fails wherever that rewrite
is not in the path.

The **run-wide default was three different values at once** — `claude-opus-4.8 @
max` in the built-in constant of all three Orchestrators, `claude-opus-5 @ high`
in this repository's tracked Config, and the contract stating the first while the
flagship consumer ran the second. It is now `claude-opus-5 @ xhigh` everywhere,
one rung below the escalation rung, so the default **reserves** the ceiling
rather than spending it and a stalled issue has somewhere left to escalate to.
That change ships in lockstep across Python, shell, and PowerShell, because the
default pair is a §11 MUST for every Orchestrator and moving one would have made
the written contract false for the other two rather than merely unimplemented.

## The resolver answers a record, not a bare pair

`resolve_iteration_model` returned `(model, effort)`, so *why* a pair had been
chosen was unrecoverable from it. Every surface that wants to say "routed from
`task-type:docs`" versus "defaulted, because the issue carried no label" had to
redo the decision from labels and Config, and the gate warnings raised along the
way were computed and thrown away — which is why per-issue routing had no gate
diagnostic in any stream.

It now answers a **Routing resolution**: the gated model, reasoning effort and
context tier; the `task-type` keys exactly as the tracker spelled them; the gate
warnings; a **Routing source** from a closed vocabulary; and the attempt's
lifecycle position. One function is the single source of routing truth.

Nothing new is displayed yet. This is deliberately the floor the readers stand
on — Pickup publishing the pair it resolved (#407), Run start reading its parsed
routing back (#410), and the Dashboard showing the routed pair per issue (#411)
are all still owed.

The context-tier gate is live and pinned against synthetic rows, and its roster
ships **empty**: extending it requires verification against the pinned harness,
and a candidate list taken on trust would have been the same class of defect the
routing table above had just been corrected for. The gate exists; only the data
is owed. Relatedly, the model roster fixture is now stamped with the CLI version
its *content* was captured against, so a correction can be told from a defect.

## The ending a session reached becomes data

The loop knew exactly why a session had ended and spent that knowledge on a
diagnostic string — three of them, flattening a timeout, a raised send, and a
failed session lifecycle into prose that nothing downstream could act on. The
one case most worth explaining reached none of them: the harness reports a
refused model call on its own Event stream and lets the session finish politely,
so an exhausted quota and a session that merely produced nothing were
indistinguishable.

**Session outcome** is now a closed five-member vocabulary — silent no-progress,
timeout, crash, an explicit declaration that no tasks remain, and content-filtered
— and a session that advanced its issue reaches none of them. **Session error**
carries the harness's own account of a failure alongside it: error type, message,
service status code and origin, classified into quota, rate limiting,
authentication, content filtering, transport, service fault, and unknown.

Recording is the whole of the job. Nothing aborts a Run, backs off, or withholds
an issue on the strength of one, so an account-level condition is still
attributed to the individual issue whose Iteration met it, exactly as before.
Whether quota deserves a Run-level stop and rate limiting deserves a delay are
real questions, and answering them by accident inside a classifier would be the
worst possible place to answer them.

Two new SDK-mapped Event literals, `session.error` and `model.call_failure`, ship
family-wide and are emitted by Python alone: both native ports shell out to the
agent binary and subscribe to no SDK stream, so each declares the literals for
vocabulary parity and emits neither — the rule every SDK-mapped type already
follows.

## A Run that was killed stops claiming it finished

`_Loop.drive` initialised its outcome to `iteration_cap` and guarded the loop
with `except Exception`. `KeyboardInterrupt` and `CancelledError` are
`BaseException`, so they passed straight through and reached the `finally` with
the initial value intact — and the Run published `iteration_cap`. On the run this
was found on, `max_iterations` was `0`, which disables the cap check entirely, so
the Run recorded the one outcome its own configuration had made unreachable. An
operator could not tell a Run that finished its work from one whose terminal was
closed.

Interrupted Runs now publish `interrupted`, and `iterations_run` counts rounds
that *finished*, floored at zero. It is deliberately not an exit status: an
interrupted Run does not choose one, the propagating `KeyboardInterrupt` does.

## `git-loopy labels` reconciles the tracker

`bootstrap_labels` ensures — it creates what is absent, leaves what exists alone,
and runs once, at whatever moment `init` happened to run. That is right for a
renamed triage role and silent about everything else: `priority` shipped and this
repository ranked every issue identically until a human created the label by
hand, the seven `task-type:` labels were absent for the same reason while routing
was reading them at Pickup, and six descriptions disagreed with the source of
record with nothing anywhere saying so.

`git-loopy labels` gives every entry in the Label vocabulary a verdict — missing,
drifted (naming the attribute), or matched — and `--apply` writes the difference
back. Reporting is the default, because a report is safe against a tracker the
operator does not own. It is additive only: a tracker label outside the
vocabulary is never reported and never deleted, and an update never renames, which
would detach every issue already carrying the label.

## Compatibility

- Every public Orchestrator identity surface reports the exact shared Release
  version `0.9.0-dev.0`: `git-loopy --version`, `wrapper.run.start`, and the
  Continuation capability manifest. The Python distribution normalises the same
  version to `0.9.0.dev0` under PEP 440.
- Release identity is independent of compatibility identity. This distribution
  implements Wrapper contract 1.19 — 1.16 at 0.8.0 — Event schema fixture 1.1
  (compatibility schema 1), Continuation contract 1.3 accepting 1.0 through 1.3,
  and Continuation record format 1.
- Measured routing remains declared Python-only in the Wrapper contract. The
  shell and PowerShell Orchestrators run the loop; they do not calibrate.
- The Runner-family Conformance gate covers the Python, shell, PowerShell, and
  Rust boundaries on every operating system each member claims, and passes on all
  of them before publication. A prerelease clears the same gate a stable Release
  does; what it does not clear is the stable platform-trust bar, which is why it
  is marked prerelease and reaches no package channel.

## Installation

This is a prerelease. It is not published to Homebrew, winget, or Scoop, it is
not what `--latest` resolves to, and an operator who wants the supported Release
should install `v0.8.0` instead.

- Download GitHub's automatic source archive for the `v0.9.0-dev.0` tag and run
  the selected Orchestrator from the extracted tree.
- Python 3.11 or newer can install the nested Python project directly from the
  tag with `uv tool install
  "git+https://github.com/bradcstevens/git-loopy@v0.9.0-dev.0#subdirectory=git-loopy/python"`.
- The clone-local shell and PowerShell installers add launchers for their native
  Orchestrators. Shell requires Bash 4+ and `jq`; PowerShell requires PowerShell 7+.

This source-only Release does not publish to PyPI and does not include signed
platform artifacts.
