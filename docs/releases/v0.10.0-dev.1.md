# git-loopy 0.10.0-dev.1

git-loopy 0.10.0-dev.1 is a **development prerelease**, not the completion of
stable 0.10.0. It publishes the work on `main` through
`848d10cbd156022dacd975dd5a22b212d8cdcac1`, with a shared prerelease identity
and these notes. The unpublished #459 detached-Run/Dashboard-client work is
deliberately excluded.

The main changes since 0.9.0 are dependency-aware issue readiness, the Python
Execution-host boundary and rolling dispatch, safer Stop and dead-Run cleanup,
and installation identity reporting. Several old Python mode switches and
Workflow Continuation are removed; this is not a drop-in compatibility promise.

## A blocked issue does not spend a session

The Python, shell, and PowerShell Orchestrators read GitHub's native one-hop
`blockedBy` relationships. A candidate with a proven open blocker is passed
over without a Strike; incomplete or unreadable dependency data is
`readiness_unprovable`, not evidence that the issue is ready.

Blocked candidates remain in the membership Pool, so a later complete refresh
during a Run can make them eligible. A Pool containing only proven blocked
issues ends as `all_blocked`, rather than masquerading as an empty Pool.
Mixed blocked and unreadable candidates end as `all_skipped`.

This path requires **GitHub CLI 2.94.0 or newer** with `blockedBy` support.
The family refuses an incapable CLI during preflight rather than working
without dependency information.

## Python dispatch is governed by its Execution host

Python Runs use rolling dispatch, with the selected **Execution host** declaring
the hard Lane ceiling. The adaptive controller can reduce the effective limit
but cannot exceed host capacity. The shipped host is **local**, derives capacity
from local CPU availability with a minimum of one Lane, and declares workspace
separation as its isolation.

Run and contribution records carry Execution-host provenance. Contribution
completion records identify the branch, completion SHA, placement, isolation
grade, and session ending. The seam contains groundwork for remote completion
and explicit host failures, but **GitHub Actions execution is not available in
this snapshot**. Unsupported host selections fail preflight rather than falling
back silently.

## Stop and cleanup preserve unfinished work

In the Python Dashboard, Stop is two-stage: the first request drains work and
prevents refill or new dispatch; the second cancels active sessions after
salvage. Operator-stopped work is distinguished from agent failure and does not
create a Strike or Demotion.

Dirty Lane workspaces are salvaged into Checkpoints before reclamation. This
preserves recoverable work; it does not promise that the next Run resumes an
abandoned Lane.

Per-Run control artifacts and advisory locks provide liveness information.
`git-loopy sweep --dry-run` reports reclaimable dead-Run residue, while
`git-loopy sweep` reclaims dead workspaces and reserved branches. Ownership
follows the reserved `git-loopy/` branch namespace rather than a path alone,
and unknown liveness is preserved rather than treated as proof of death.

## Terminal behavior and defaults

Python no longer exposes an operator-selected parallelism mode. `--parallel`,
`GIT_LOOPY_MAX_PARALLEL`, `--interactive`, `--no-interactive`, and
`GIT_LOOPY_INTERACTIVE` are retired rather than compatibility aliases.
A terminal selects the live Dashboard automatically; non-terminal output uses
the line printer. The shell and PowerShell members retain their own mode
controls.

Textual is now a base Python dependency and the separate `[tui]` extra is gone.
The in-process Dashboard still ships in this snapshot: detaching returns the
Run to scrollback, and a Dashboard fault is surfaced before falling back to the
line printer. Closing the terminal is **not** the detached-Run guarantee planned
by #459.

The built-in default pair moves to **`claude-opus-5 @ max`**. Consequently, the
built-in escalation pair is identical to the default for unclassified work;
routed task-type pairs remain below `max`, and explicit escalation configuration
still applies. Existing saved configuration continues to take precedence over
built-in defaults.

The startup model/reasoning picker remains opt-in through `--select-model` or
`GIT_LOOPY_MODEL_SELECT=1`.

## Installation identity and compatibility

`git-loopy info` and `git-loopy info --json` report installation facts, including
the artifact, proven channel, Release version, resolved commit, published-Release
status, and edge-install status.

**Workflow Continuation is removed, not deprecated**, across Python, shell, and
PowerShell, including its capability checks and Event namespace. Consumers of
the retired contract must migrate rather than rely on an alias.

Every public Orchestrator Release identity reports `0.10.0-dev.1`. Python
distribution metadata uses its equivalent PEP 440 spelling, `0.10.0.dev1`.
Release identity remains separate from Wrapper-contract and Event-schema
compatibility.

## What this prerelease does not claim

The stable `v0.10.0` milestone remains open. This publication does not close
#436, #467, #516, #517, #518, or #519, and does not claim that the planned
per-issue release automation or the unfinished `doctor` work has shipped.

This is a **source-only publication**: GitHub's automatic source archives and
installation from the tag. It does not publish to PyPI, Homebrew, winget, or
Scoop, and it attaches no compiled TUI helper.

## Installation

The default stable installation remains pinned to `v0.9.0`. To try this
prerelease explicitly with Python 3.11 or newer:

```sh
uv tool install "git+https://github.com/bradcstevens/git-loopy@v0.10.0-dev.1#subdirectory=git-loopy/python"
```

Alternatively, extract the source archive for `v0.10.0-dev.1` and run the
selected Orchestrator. Shell requires Bash 4+ and `jq`; PowerShell requires
PowerShell 7+.
