# git-loopy 0.10.0

git-loopy 0.10.0 is the stable Release line accumulated since 0.9.0. It adds
dependency-aware scheduling, host-governed rolling dispatch, detached terminal
Runs, safer recovery, and a Python installation lifecycle. It also removes
Workflow Continuation: this is not a drop-in compatibility release for
consumers of that command or its Event vocabulary.

## Terminal interaction changes

The Dashboard is now the default terminal interface for Python Runs. Use
`--no-interactive` or `GIT_LOOPY_INTERACTIVE=0` to retain the line-printer
view. Interactive setup is now a fullscreen wizard, so piping numbered answers
into `git-loopy init` no longer works; use `git-loopy init --yes` for unattended
setup.

## Runs schedule work from facts the tracker already knows

The Python, shell, and PowerShell Orchestrators now read GitHub's native,
one-hop `blockedBy` relationship. An issue with an open blocker stays in the
Pool but is skipped without consuming a session or a Strike; it becomes
eligible on a later refresh when its blockers close. An incomplete dependency
read is reported as `readiness_unprovable`, rather than treated as proof that
the issue is ready. A Run whose remaining work is blocked reports that state
instead of looking empty.

This requires GitHub CLI 2.94.0 or newer. An incapable CLI is refused at
preflight rather than silently running without dependency information.

The Python Orchestrator always uses rolling dispatch. Its Execution host sets
the hard Lane ceiling, while the controller may lower the effective limit for
observed pressure and integration backlog. `local` remains the default host;
`github-actions` is available through `--execution-host` or
`GIT_LOOPY_EXECUTION_HOST` and preflights the target repository before it
reserves work. The remote host requires `run-preflight.yml`,
`lane-contribution.yml`, and the shared setup action in that repository; a
failed preflight starts no Lane and spends no Strike.

Terminal Python Runs now detach the worker and keep the terminal as an attach
client. When `git-loopy-tui` is available it provides the live view; otherwise
the client follows the trace through the line-printer fallback. Stop remains
two-stage: the first request drains work without refilling, and the second
cancels active work after salvage. Dirty Lane work is checkpointed before
reclamation, and `git-loopy sweep --dry-run` reports dead-Run residue before
`git-loopy sweep` removes only work it can prove belongs to a dead Run.

## Routing is explicit when an operator needs it

The Python Runner adds the opt-in `static` Route policy. With
`--route-policy static` (or the matching configuration), the selected model,
reasoning effort, and context tier are verified against the authenticated
harness that the Run starts. An unsupported or unverifiable selection fails
before work begins; git-loopy does not silently downgrade it. The chosen static
route remains fixed across retries unless the operator explicitly configured an
escalation rung.

Resolved context tiers now reach every Python session, including remote Lane
contributions. The recommended `test` route moves from the withdrawing
`gemini-3.6-flash` to `claude-sonnet-5 @ high`. The run-wide default remains
`claude-opus-5 @ max`; saved configuration continues to take precedence.

## Installation, diagnostics, and Release operations

Python now exposes `info`, `doctor`, `update`, `upgrade`, and `uninstall`.
`info` describes the installation's identity and managed assets. `doctor`
checks the same environment and Skill-policy preconditions a Run checks,
reports every blocker in one pass, and repairs only safe Skill-policy problems
behind `doctor --apply`. `update` refreshes machine-local assets and repairs
retired routing keys without overwriting customized prompt prose; `upgrade`
moves the proven install channel to a published Release and then updates it.
`uninstall` preserves project scope and Run logs unless `--all` is explicit, and
refuses outright while a Lane is live rather than collecting an agent's
uncommitted work.
These lifecycle commands are Python-Runner features, not new shell or
PowerShell Orchestrator commands.

Root help now groups every Python management command by category; `git-loopy
help` is its bare-word alias. Shell completions can consume the same inventory
through the schema-versioned `git-loopy commands --json` output.

Release-line advances now infer a closed `semver:` Bump class at Pickup,
advance the shared Release version after Integration, and publish that advance
to the Event stream and Dashboard. A closed `vX.Y.Z` milestone promotes its
matching development line to stable. Workflow Continuation and its capability
checks, command namespace, and `wrapper.continuation.*` Events are removed;
the Wrapper contract is 2.0.

## Source-only availability and installation

This stable Release is **source-only**. GitHub supplies its automatic source
archives, but protected release-signing credentials are unavailable: there is
no PyPI publication, signed TUI helper, Homebrew update, winget submission, or
Scoop update.

Install the Python Runner from this tag with Python 3.11 or newer:

```sh
uv tool install "git+https://github.com/bradcstevens/git-loopy@v0.10.0#subdirectory=git-loopy/python"
```

To run the source Orchestrators directly, the shell member requires Bash 4+
and `jq`; the PowerShell member requires PowerShell 7+.
