# git-loopy 0.11.0-dev.7

This development prerelease is the project's first **artifact-bearing**
publication. Every prerelease up to and including
[v0.11.0-dev.6](https://github.com/bradcstevens/git-loopy/releases/tag/v0.11.0-dev.6)
was source-only and carried zero assets, so no supported installation could ever
resolve a Dashboard helper by download. This one publishes the helper archives at
their canonical public URLs ([#592](https://github.com/bradcstevens/git-loopy/issues/592)).

It is not a stable Promotion: the Release target remains `0.11.0`, and stable
`v0.10.0` is unchanged.

## The downloadable helper baseline

- `git-loopy/conformance/release-trust.json` now declares
  `"distribution_mode": "artifact-bearing"`. That declaration is the **only**
  thing that schedules the helper build, signing, attachment, and
  package-channel jobs. Secret presence still cannot choose the mode, and a
  missing prerequisite still cannot silently downgrade the promise to
  source-only — the boundary [#582](https://github.com/bradcstevens/git-loopy/issues/582)
  established is unchanged, only the value this repository declares has moved.
- The helper is published for the declared target set, including the
  `git-loopy-tui-aarch64-apple-darwin.tar.xz` archive whose absence produced the
  reported 404. Each archive ships with its checksum and trust receipt, and the
  publication job verifies the complete promised set by downloading it back from
  the canonical public URLs before the Release is considered delivered.
- Prerelease trust requirements are unchanged: checksums and trust receipts are
  required, and the stable-only gates — Developer ID signing, macOS
  notarization, Windows publisher evidence, and build attestation — are neither
  bypassed nor weakened for this prerelease.

### What this changes for an operator

An installation no longer needs a Rust toolchain, a source checkout, or a
hand-built binary to obtain the Dashboard helper. `git-loopy update` — including
the `update` that `git-loopy upgrade` chains — resolves the newest published
helper at or below the installed Runner Release, verifies its checksum, identity,
and Event-schema compatibility, and activates it. A failed activation still
restores the previous helper and its resolved-Release record together.

Runners that remain on an older **source-only** Release are unaffected by this
change and keep their existing behaviour: they retain a matching local helper
when one is present, and otherwise resolve the newest eligible *older* published
helper once a baseline exists to resolve.

## Known gap: Windows attachment

The Windows helper is built and published like every other declared target, but
it does **not** yet implement the Runner's attachment/control protocol —
`git-loopy/tui/src/main.rs` returns `attach mode is not supported on this
platform` on non-Unix targets. A Windows operator therefore receives a verified,
identity-correct helper that the Python Runner cannot attach to as a Dashboard
client.

This is disclosed rather than worked around. It is the outstanding obligation of
[#459](https://github.com/bradcstevens/git-loopy/issues/459), and
[#592](https://github.com/bradcstevens/git-loopy/issues/592) stays open until that
attachment support lands and the complete helper set can be certified against the
real protocol. No declared target was dropped to make this Release look complete,
and stdin projection is not claimed as attachment proof.

## Release-line hygiene

Existing public tags remain immutable. `v0.11.0-dev.6` and every earlier
source-only promise keep exactly the assets they were published with; none is
retrofitted with helpers. This Release advances the line to `0.11.0-dev.7`
through the ordinary Release-version bump rather than by moving a tag, inventing
a milestone, or assigning a Release target outside the existing policy.
