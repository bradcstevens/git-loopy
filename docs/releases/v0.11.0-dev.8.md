# git-loopy 0.11.0-dev.8

This development prerelease moves the Python Runner to Copilot SDK 1.0.14, adds
four new models to the built-in model roster, and brings the Python-local Dynamic
routing default onto `main`. That work had been completed and closed on a branch,
but never merged. The Release target is still `0.11.0` and stable `v0.10.0` is
unchanged, so this is not a stable Promotion. Like
[v0.11.0-dev.7](https://github.com/bradcstevens/git-loopy/releases/tag/v0.11.0-dev.7),
it includes the prerelease Dashboard helper archives.

## Before you upgrade: a local Run needs a Route policy

A local Run now refuses before any Agent work if either Config scope holds values
but neither selects a Static or Dynamic **Route policy**. `git-loopy doctor`
reports the same refusal. Nothing prompts you or writes Config to settle this,
so record the choice once:

```sh
git-loopy update --project --routing keep      # records route_policy = "static"
git-loopy update --project --routing migrate   # records route_policy = "dynamic"
```

Use `--global` instead to record the choice for every repository. A project
inherits an explicit global choice. **Keep** leaves your saved routes and run-wide
default in charge. **Migrate** keeps every `[routing]` row you wrote and uses
Dynamic routing only for work those rows don't cover. Migrate needs your own
`GIT_LOOPY_ARTIFICIAL_ANALYSIS_API_KEY`, kept outside Config, and a verified
`[route_associations]` table. Either choice turns on strict live validation of
routes. `--route-policy` or `GIT_LOOPY_ROUTE_POLICY` supplies a policy for one
invocation only, and `unselected` keeps the legacy path for that Run.

Dynamic routing is now the declared default for unpinned new work in Python-local
Runs. A local Run with no Config and no named policy also refuses before work.
A fresh `git-loopy init --yes` records `route_policy = "dynamic"` without adding
Static rows, and the next Run refuses until `git-loopy init --routing migrate`
collects the Dynamic limits
([#567](https://github.com/bradcstevens/git-loopy/issues/567)).

## Copilot SDK 1.0.14 and new models

- `github-copilot-sdk` moves from `1.0.13` to `1.0.14`, which moves the managed
  Copilot CLI from `1.0.83` to `1.0.85`. Both come from the Microsoft corporate
  feed ([#636](https://github.com/bradcstevens/git-loopy/pull/636),
  [#638](https://github.com/bradcstevens/git-loopy/issues/638)). Upstream's 1.0.15
  prereleases were not on that feed and were not taken from anywhere else.
- The model roster adds `grok-4.7` (`low` to `high`), `claude-opus-5.5` (`low` to
  `max`), and `gpt-6-luna` and `gpt-6-sol` (`none` to `max`). Each was captured
  from a live model listing through two Copilot CLI versions. The seven
  compatibility entries that live listings don't return are kept.
  `gemini-3.8-flash` stays off the roster and still gets a warning and passes
  through unchanged.
- `python -m git_loopy.sdk_feed` reports when the corporate feed has an SDK
  release newer than the pin. It never changes the pin
  ([#639](https://github.com/bradcstevens/git-loopy/issues/639)).
- The cache of models the harness has offered can no longer turn a successful
  capability read into a traceback at Run start
  ([#641](https://github.com/bradcstevens/git-loopy/pull/641)).

## Routing

- A selected Static route on GitHub Actions proceeds only when that host reports
  its own model listing and both that listing and the local one accept the route.
  A Static Pickup records whether the listing offered an effort setting
  ([#567](https://github.com/bradcstevens/git-loopy/issues/567)).
- Publication writes separate `model_id:`, `model_context:` and `model_effort:`
  labels instead of the truncated `git-loopy-route:` label. A pending delivery
  that used the old label is converted on restart
  ([#614](https://github.com/bradcstevens/git-loopy/issues/614)). `model_context`
  is updated from the context window reported by the session doing the work
  ([#615](https://github.com/bradcstevens/git-loopy/issues/615)).
- `git-loopy route-labels migrate` reports on the old Route labels across every
  open and closed issue, and `--apply` migrates them to the new labels. Stop or
  upgrade every Runner that publishes Route labels before running `--apply`
  ([#616](https://github.com/bradcstevens/git-loopy/issues/616)).
- Routing in the shell and PowerShell Orchestrators is still deferred. None of
  this adds routing for Subagents or Integration.

## Planning documents stay out of the Pool

- An issue labelled `wayfinder:map` that carries `ready-for-agent` is kept out of
  the Pool as a `planning_document` in all three Orchestrators, and pinning it
  with `--issue` refuses
  ([#635](https://github.com/bradcstevens/git-loopy/issues/635)).
- `/to-spec` now publishes specs as `ready-for-human`, and `/triage` never puts
  `ready-for-agent` on a planning document. The pinned Skill catalog moves to
  that revision ([#627](https://github.com/bradcstevens/git-loopy/issues/627)).
- `git-loopy labels` reports open planning documents that carry
  `ready-for-agent`, and `--apply` removes only that label
  ([#628](https://github.com/bradcstevens/git-loopy/issues/628)).
- A test now fails if the `wayfinder:` label set git-loopy declares stops matching
  the pinned `/wayfinder` Skill. Another fails if the Pool stops excluding the map
  label that Skill writes
  ([#630](https://github.com/bradcstevens/git-loopy/issues/630)).

## Skills catalog

- A CI job fetches the pinned Skill catalog and runs the three
  cross-repository checks that used to be skipped
  ([#632](https://github.com/bradcstevens/git-loopy/issues/632)).
- `python -m git_loopy.skill_candidate` checks a local `git-loopy-skills` checkout
  offline before the pin moves
  ([#633](https://github.com/bradcstevens/git-loopy/issues/633)).
- An Iteration may make an issue's matching change in `git-loopy-skills`. That
  change is published and checked before the pin moves (ADR-0064,
  [#634](https://github.com/bradcstevens/git-loopy/issues/634)).

## Dashboard

- The Dashboard header now shows Wind-down and the Execution host
  ([#464](https://github.com/bradcstevens/git-loopy/issues/464)).

## Wrapper contract 2.10

The Wrapper contract moves to version 2.10. It adds the Python-local Dynamic
default and the refusal of a Run with no Config, exact Route-label publication,
the optional `effort_configurable` field on Pickup, Static routes approved by a
remote host's own model listing, and the Wayfinder-map Pool exclusion.
Everything that shipped in 2.9 is unchanged. The Event wire format stays at
1.2, and the Dashboard helper now reports `wrapper_contract_version` `2.10`.

## Known gap: Windows attachment

This is unchanged from `v0.11.0-dev.7`. The Windows helper is built, verified and
published, but it can't attach to a Run yet
([#459](https://github.com/bradcstevens/git-loopy/issues/459)).
