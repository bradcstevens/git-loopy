# git-loopy 0.8.0

git-loopy 0.8.0 is the second published Release, and it carries two things at
once: the whole of phase 2, which was prepared as 0.7.0 and never published, and
the Calibration and measured-routing milestone that landed on top of it.

The Runner family is unchanged in shape — a Python reference Orchestrator, native
shell and PowerShell Orchestrators, and a Rust Dashboard core, all pinned against
the same Conformance fixtures.

## Why 0.8.0, and what became of 0.7.0

0.7.0 was prepared in full: the version moved in every seam, its notes were
edited, and its five milestones' worth of content merged. Its tag was never
created, so `source-release.yml` never ran and nothing was ever published. A
milestone's content reaching `main` and a Release publishing it are two events,
and this is what it looks like when they come apart.

Publishing 0.7.0 now would name a tree that `main` left behind a milestone ago.
0.8.0 carries that content forward instead, and 0.7.0 is a version that never
shipped. The `v0.7.0` milestone is closed regardless, because its content *is*
on `main` — the milestone records delivery, and the tag records publication.

## Calibration: routing chosen by measurement, not judgment

A Run can now decide which model works a Task type because it *measured* one,
rather than because someone guessed. `git-loopy calibrate` walks the price
staircase built from the live roster and the Rate card, cheapest pair first, and
keeps the first that clears the gate five times out of five.

What it measures against is a **Proving set** mined from this repository's own
closed issues: a candidate is admitted only if its task actually fails before its
fix and passes after, so a task that proves nothing never costs anything. Each
**Trial** replays one such issue in its own worktree at the historical commit and
is scored by that fix's own tests. Trials run concurrently across worktrees under
a ceiling that is elapsed wall clock and AI Credits, not a Trial count.

A Trial is deliberately not an Iteration. It takes no Strike, claims no Run
attribution, and publishes its own Events, so a Calibration cannot contaminate
the record of the work the loop is actually doing.

Nothing spends without being asked. `calibrate --status` reports what the corpus
supports — the Routed pair per Task type, the tier behind it, the Proving tasks
that exist, and whether the live roster now offers an unmeasured pair cheaper
than the measured winner. `calibrate --dry-run` reports what a Calibration would
cost. Neither runs a Trial, spawns a session, creates a worktree, or consumes a
credit. A bare `git-loopy calibrate` prints its plan and asks before the first
Trial; `--yes` is required to spend where there is nobody to ask.

**Demotion** closes the loop in the other direction: a measured pair that stops
making progress steps back up the staircase and is written as `provisional`, a
routed pair that no longer has a measurement standing behind it. A Run also tells
you when re-calibrating could change an answer, rather than waiting to be asked.

Calibration and measured routing are Parallel-mode features and now say so:
`calibrate` refuses to spend when the Lane cap resolves to 1.

The Task-type taxonomy is closed at seven keys — planning, review,
implementation, test, docs, chore, bugfix — and `init` creates their labels. A
classifier infers an issue's Task type from the issue's own content and writes
the inference back to the tracker, so the routing decision and its input are both
visible on the issue rather than only inside a Run.

The measured tier is recorded in the Wrapper contract and declared **Python-only**
there, so the shell and PowerShell Orchestrators are not silently assumed to
implement it.

## The runner picks the oldest eligible issue

Eligible issues now have one total order, pinned by Conformance and computed over
the same read in every family member. The candidate fetch reaches the end of the
backlog with timestamps rather than stopping at the first page, Parallel mode
works its backlog oldest-first through that order, and the `priority` label is a
human assertion that reorders without changing eligibility.

Selection is a record rather than a log line: a serial Iteration binds its issue
before the session starts, and Pickup and skip Events make the choice visible in
replay and on the Dashboard. `git-loopy run --issue N` pins one issue for one
invocation — deliberately neither a label nor an environment variable, both of
which would point every concurrent Run at the same issue — and it bypasses order
and nothing else.

## The Skill contract moves upstream

git-loopy's contract-carrying Skills are published to
[`bradcstevens/git-loopy-skills`](https://github.com/bradcstevens/git-loopy-skills)
as their source of record. This repository pins an immutable revision, `init`
installs it into git-loopy's own config home, and every Run refreshes that
install — which is the only Skill source a Run reads.

## The Activity band an operator sizes

The Rust Dashboard grows a mouse. The Activity band has a drag handle and
click-to-collapse, with the keyboard path and the underlying state machine intact
and family parity held across the fixture seam.

## What 0.7.0 had carried

Everything prepared for 0.7.0 publishes here for the first time.

**Closed-world Skill policy.** A Run resolves and freezes its Skill policy before
it starts, so the same Run performed twice reads the same Skills. `git-loopy init`
establishes a policy, legacy Config is migrated before a Run begins, and a policy
can be synced from Copilot or edited with the shared plain-terminal picker. The
shell and PowerShell Orchestrators fail closed on it rather than proceeding with
whatever they find.

**Rolling dispatch and Parallel mode.** Issues are dispatched into Lanes and
integrated under a gate that must be green before a Lane's contribution merges,
with the AGENTS.md feedback-loop table as that gate's input.

**Family-wide Dashboard insights.** An additive insight contract with a shared
fixture seam, and semantic parity enforced across the family: authoritative issue
activation, live Context fill, normalized Iteration and accounting rollups,
closure timing, and truthful streaming with immutable issue binding from Python,
shell, and PowerShell alike.

**The shared TUI helper.** `git-loopy-tui` is a standalone Rust helper that
renders the Dashboard, discovered by any family member and supervised from the
shell and PowerShell Orchestrators as well as Python. It negotiates Event-schema
capabilities rather than assuming Release equality, and a Run whose helper stops
reading falls back to raw JSONL on stdout instead of failing.

**The gate 0.7.0 had to clear.** Publication is gated on Runner-family
Conformance, and that gate had been red on `main` — five of its seven jobs
failing deterministically while every suite passed on a maintainer's machine.
Four of those failures were assertions that pinned the environment rather than
the product: a Skill-scan exemption naming a gitignored directory no checkout has
([#386](https://github.com/bradcstevens/git-loopy/issues/386)); a Rust test that
panicked on the broken pipe left by a helper correctly reporting it had no
controlling terminal
([#387](https://github.com/bradcstevens/git-loopy/issues/387)); a shell assertion
requiring SIGPIPE at its default in the agent, which POSIX forbids any shell from
restoring once it was ignored on entry
([#388](https://github.com/bradcstevens/git-loopy/issues/388)); and the two
Windows-only failures, where the TUI installer's staging slot and the
Orchestrator's discovery slot disagreed because only one of them knew Windows
names an executable by its extension, and a `gh` resolving to a `.cmd` shim was
handed a paginated query whose `&` `cmd.exe` re-read as a command separator
([#315](https://github.com/bradcstevens/git-loopy/issues/315)).
[#385](https://github.com/bradcstevens/git-loopy/issues/385) tracked the whole of
it.

## Compatibility

- Every public Orchestrator identity surface reports the exact shared Release
  version `0.8.0`: `git-loopy --version`, `wrapper.run.start`, and the
  release identity surfaces.
- Release identity is independent of compatibility identity. This distribution
  implements Wrapper contract 1.16 — 1.4 at the time 0.7.0 was prepared — Event
  schema fixture 1.1 (compatibility schema 1).
- Measured routing is declared Python-only in the Wrapper contract. The shell and
  PowerShell Orchestrators run the loop; they do not calibrate.
- The Runner-family Conformance gate covers the Python, shell, PowerShell, and
  Rust boundaries on every operating system each member claims, and passes on all
  of them before publication.

## Installation

- Download GitHub's automatic source archive and run the selected Orchestrator
  from the extracted tree.
- Python 3.11 or newer can install the nested Python project directly from the
  `v0.8.0` tag with `uv tool install
  "git+https://github.com/bradcstevens/git-loopy@v0.8.0#subdirectory=git-loopy/python"`.
- The clone-local shell and PowerShell installers add launchers for their native
  Orchestrators. Shell requires Bash 4+ and `jq`; PowerShell requires PowerShell 7+.

This source-only Release does not publish to PyPI, Homebrew, winget, or Scoop,
and does not include signed platform artifacts or a compiled TUI helper.
