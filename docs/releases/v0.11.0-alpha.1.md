# git-loopy 0.11.0-alpha.1

This alpha prerelease restarts the `0.11.0` Release line under the Semantic
Versioning 2.0.0 prerelease stages `alpha`, `beta`, and `rc` (ADR-0066). It
carries everything the retired `0.11.0-dev.1` through `0.11.0-dev.8`
development prereleases carried; those tags and GitHub Releases were removed,
and their notes are folded in below so the stable `0.11.0` draft still
composes from them.

## Formerly 0.11.0-dev.1

This development prerelease collects all completed work on `main` since
`v0.10.0`: #508, #510, #529, #530, and #531. It starts the next development
Release line; it is not a stable Promotion.

### Wizard-first setup

The fullscreen setup wizard is now the only interactive renderer. The numbered
setup and Skill pickers are removed, Textual is a base dependency, and the old
`[tui]` installation extra is no longer needed. Backward navigation and the
review-before-Save boundary remain available; non-terminal setup requires
`git-loopy init --yes` instead of piped numbered answers (#508).

The setup documentation now covers keyboard navigation, cancellation without
writes, unattended defaults, and the Dashboard default. Use `--no-interactive`
or `GIT_LOOPY_INTERACTIVE=0` to choose the line-printer view (#510).

### Safer installation lifecycle

`git-loopy uninstall` now completes its machine-local safety contract: it shows
the removal plan and requires confirmation, preserves repository contents and
Run logs by default, refuses live or unprovably dead Lane work, and checks that
removal paths have not changed since confirmation. Repository scope is included
only with explicit `--all`; a machine-local removal never takes the repository
with it. The associated Run lock no longer hangs or fails Runs on hosts that
cannot provide advisory locking (#529).

The operator reference distinguishes `update`, `upgrade`, and `uninstall`,
including their scope, flags, exit behavior, provenance safeguards, and refusal
paths. These management commands belong to the Python Runner; this Release does
not add them to the shell or PowerShell Orchestrators (#531).

### Discoverable commands

Root `--help` now groups management commands by category, `git-loopy help` is
its bare-word alias, and `git-loopy commands --json` exposes the same inventory
through a schema-versioned machine-readable surface (#530).

### Source-only availability and installation

This prerelease publishes committed notes and GitHub's automatic source
archives. It does not update package channels or publish compiled TUI helpers.
The Python Runner retains its line-printer fallback when no compatible helper
is installed.

Install or replace the user-global Python Runner with Python 3.11 or newer:

```sh
uv tool install --force "git+https://github.com/bradcstevens/git-loopy@v0.11.0-dev.1#subdirectory=git-loopy/python"
```

Use the explicit development tag: an unqualified `git-loopy upgrade` selects
the latest stable Release, not this prerelease.

## Formerly 0.11.0-dev.7

### The downloadable helper baseline

- `git-loopy/conformance/release-trust.json` now declares
  `"distribution_mode": "artifact-bearing"`. That declaration is the **only**
  thing that schedules the helper build, signing, attachment, and
  package-channel jobs. Secret presence still cannot choose the mode, and a
  missing prerequisite still cannot silently downgrade the promise to
  source-only — the boundary [#582](https://github.com/bradcstevens/git-loopy/issues/582)
  established is unchanged, only the value this repository declares has moved.
- The helper is published for the declared target set, including the
  `git-loopy-tui-aarch64-apple-darwin.tar.xz` archive whose absence produced the
  reported 404. Each archive ships with its checksum and trust receipt, and the
  publication job verifies the complete promised set by downloading it back from
  the canonical public URLs before the Release is considered delivered.
- Prerelease trust requirements are unchanged: checksums and trust receipts are
  required, and the stable-only gates — Developer ID signing, macOS
  notarization, Windows publisher evidence, and build attestation — are neither
  bypassed nor weakened for this prerelease.

#### What this changes for an operator

An installation no longer needs a Rust toolchain, a source checkout, or a
hand-built binary to obtain the Dashboard helper. `git-loopy update` — including
the `update` that `git-loopy upgrade` chains — resolves the newest published
helper at or below the installed Runner Release, verifies its checksum, identity,
and Event-schema compatibility, and activates it. A failed activation still
restores the previous helper and its resolved-Release record together.

Runners that remain on an older **source-only** Release are unaffected by this
change and keep their existing behaviour: they retain a matching local helper
when one is present, and otherwise resolve the newest eligible *older* published
helper once a baseline exists to resolve.

### Known gap: Windows attachment

The Windows helper is built and published like every other declared target, but
it does **not** yet implement the Runner's attachment/control protocol —
`git-loopy/tui/src/main.rs` returns `attach mode is not supported on this
platform` on non-Unix targets. A Windows operator therefore receives a verified,
identity-correct helper that the Python Runner cannot attach to as a Dashboard
client.

This is disclosed rather than worked around. It is the outstanding obligation of
[#459](https://github.com/bradcstevens/git-loopy/issues/459), and
[#592](https://github.com/bradcstevens/git-loopy/issues/592) stays open until that
attachment support lands and the complete helper set can be certified against the
real protocol. No declared target was dropped to make this Release look complete,
and stdin projection is not claimed as attachment proof.

### Release-line hygiene

Existing public tags remain immutable. `v0.11.0-dev.6` and every earlier
source-only promise keep exactly the assets they were published with; none is
retrofitted with helpers. This Release advances the line to `0.11.0-dev.7`
through the ordinary Release-version bump rather than by moving a tag, inventing

### Before you upgrade: a local Run needs a Route policy

A local Run now refuses before any Agent work if either Config scope holds values
but neither selects a Static or Dynamic **Route policy**. `git-loopy doctor`
reports the same refusal. Nothing prompts you or writes Config to settle this,
so record the choice once:

```sh
git-loopy update --project --routing keep      # records route_policy = "static"
git-loopy update --project --routing migrate   # records route_policy = "dynamic"
```

Use `--global` instead to record the choice for every repository. A project
inherits an explicit global choice. **Keep** leaves your saved routes and run-wide
default in charge. **Migrate** keeps every `[routing]` row you wrote and uses
Dynamic routing only for work those rows don't cover. Migrate needs your own
`GIT_LOOPY_ARTIFICIAL_ANALYSIS_API_KEY`, kept outside Config, and a verified
`[route_associations]` table. Either choice turns on strict live validation of
routes. `--route-policy` or `GIT_LOOPY_ROUTE_POLICY` supplies a policy for one
invocation only, and `unselected` keeps the legacy path for that Run.

Dynamic routing is now the declared default for unpinned new work in Python-local
Runs. A local Run with no Config and no named policy also refuses before work.
A fresh `git-loopy init --yes` records `route_policy = "dynamic"` without adding
Static rows, and the next Run refuses until `git-loopy init --routing migrate`
collects the Dynamic limits
([#567](https://github.com/bradcstevens/git-loopy/issues/567)).
