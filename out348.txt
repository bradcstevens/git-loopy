## #343 makes this cleaner than expected — no carve-out needed

Two findings from [#343](https://github.com/bradcstevens/git-loopy/issues/343) change the shape of this ticket.

**1. shell and PowerShell declare no Execution host support *cleanly*, not as an exception.** #343 §5 scoped the seam to **Lane contributions only** — a serial **Iteration**, **Integration**, and the entire shell/PowerShell loop are in-place work on the orchestrator's own checkout, with no host binding at all.

So the non-Python members are not "missing" a capability. They **never had a contribution to place.** That removes the awkwardness this ticket anticipated in *"whether declaring no remote host makes a member second-class"* — there is no grade of second-classness in having no Lanes, because the Execution host is a property of a Lane contribution and they have none. The honest framing is that they do not implement **Parallel mode**, which is already true, already declared, and already documented by ADR-0013.

**2. The declaration mechanism already exists — and already refuses.** Worth confirming before designing a new one:

- `lib/orchestrator.sh:994-1020` — `git_loopy_assert_parallel_supported` errors with *"this distribution has no Rolling dispatch scheduler, so it cannot fill a second Lane"* whenever a Lane cap > 1 is requested and `parallel_capabilities.parallel_mode` is false, read via `jq -r '.parallel_mode' <<<"$GIT_LOOPY_PARALLEL_CAPABILITIES_JSON"` (`lib/orchestrator.sh:1014`).
- `GitLoopy.Orchestrator.psm1:1022-1065` — `Get-GitLoopyParallelCapabilities` mirrors it: *"a Lane cap of $LaneCap was requested, but the PowerShell Orchestrator declares parallel_mode unsupported"*.

So there is a **shipped precedent** for a machine-readable capability declaration that is (a) consulted before work starts and (b) **fails loudly rather than degrading silently** when a caller asks for what a member cannot do. Your bullet on *"what happens when a caller asks for a host a member does not support"* has a working answer in the codebase to either adopt or consciously reject. Note it contrasts with the `loop.py:1914` precedent you cited (degrade Parallel mode entirely to serial) — the family currently does **both**, in different places, and that inconsistency is worth naming.

## What #343 adds to your decision list

- **Whether host support is even a separate declaration, or a consequence of declaring `parallel_mode`.** If the Execution host binds only Lane contributions, then `parallel_mode: false` already *implies* "no Execution host". A separate flag might be redundant — or might be the right place to say *which* hosts a parallel-capable member supports. Decide which.
- **Placement and isolation grade are declared by the host, not by the member.** Keep the two declarations distinct: a *member* declares which hosts it can drive; a *host* declares its placement and **isolation grade**. Conflating them would make a member responsible for asserting an isolation property it does not control.
- **The truthfulness question has a new angle.** #343's refusals mean a conformant host must *not* silently retry, must *not* write to the tracker, and must *not* mint identity. Those are behaviours a fixture could plausibly assert against a member's declaration — which is a more meaningful conformance target than "does it have the field".

**Resolved.** A member declares Execution-host support in the **parallel capability manifest** on `wrapper.run.start` — not in the Continuation capability manifest, and not in a new declaration of its own. The instrument the ticket went looking for already exists, one manifest over from where it looked, and putting the declaration in the right one is what keeps the blast radius to a single contract.

Six decisions, in the order they had to be taken.

---

## 1. The ticket offered two homes. There is a third, and it is the right one.

The ticket asked whether host support belongs in the **Continuation capability manifest** or in a separate declaration. Both were wrong, because the family already carries **two** capability manifests, and the ticket only knew about one:

| Manifest | Where it lives | What it answers |
| --- | --- | --- |
| **Continuation capability manifest** | `continuation.py:30-84`, off-stream via `continuation capabilities` | What Continuation records can this member produce and consume? |
| **`insight_capabilities`** | on every `wrapper.run.start` (`wrapper-contract.md:495`) | What can this Orchestrator **observe**? |
| **`parallel_capabilities`** | on every `wrapper.run.start` (`wrapper-contract.md:572`) | What can this Orchestrator **schedule**? |

*Where a Lane contribution executes is a scheduling fact.* It is the placement half of the dispatch decision, made by the same component, fixed for the same lifetime, and consumed by the same reader. `parallel_capabilities` is already defined in the contract as the manifest for exactly that question.

**Why not the Continuation manifest — and this is a category error the glossary names itself.** `CONTEXT.md:99` defines it as a declaration that *"describes capability but grants no execution authority."* Recording *where work executes* in the manifest defined as granting no execution authority is not a stretched fit; it is the one thing that entry rules out. Three further facts make it structural rather than aesthetic:

- Its consumer is **`verification.py`**, which judges a distribution against named **profiles** at **setup time** — `init.py:624` *"Never starts the loop."* An Execution host is meaningless before a Run exists.
- It is **not on the Event stream**. #352 made the Dashboard a client that reads a trace and *never talks to a host*; a fact it cannot read from the trace is a fact it does not have.
- Its keys are contract versions, tracker adapters, Instruction handlers, evaluators and operations. Nothing in a Run's execution boundary has a Continuation-contract meaning.

**Why not a fourth declaration.** A new manifest earns its place when the new fact has a different **subject** or a different **lifetime** than every existing one. This has neither: same subject as `parallel_capabilities` (the member's scheduling half), same lifetime (fixed for the binary). A fourth manifest would be a synonym with its own version skew.

## 2. Is a declaration even needed? Half of one — and only the affirmative half.

The #343 follow-up on this ticket asked whether host support is *"a consequence of declaring `parallel_mode`"*. It is, in one direction only, and the asymmetry is the decision:

- **Negative, derivable.** #343 §5 scoped the seam to **Lane contributions only**. No Lanes ⇒ no contribution to place ⇒ no host. `parallel_mode: false` already entails it.
- **Affirmative, not derivable.** `parallel_mode: true` says there are Lanes. It says nothing about *where* they may run. Python supports `local` today and `github-actions` after #350 ships; that is a real fact nothing else carries.

So the declaration is needed, and it is **subordinate to `parallel_mode`** exactly as the four existing rolling capabilities are. The contract's *"`parallel_mode: false` is not one `false` among five"* rule (`wrapper-contract.md:597`) extends by one clause and no new doctrine:

> `parallel_mode: false` ⇒ `execution_hosts` is **empty**. `execution_hosts` non-empty ⇒ `parallel_mode: true`.

**Empty, not absent.** The distinction is load-bearing and the contract already paid for the lesson once, on `rate_card`: an omitted key leaves a Dashboard *"unable to tell **this Orchestrator cannot report a rate** from **this Run's prices failed to load**, which is the collapse a separate declaration exists to end."* Same collapse here. Every member declares the key; two of the three declare `[]`, which reads as *"I place no contributions anywhere, because I have none to place"* — a statement, not a silence.

## 3. Granularity: an additive list, on the `rate_card` template. Two facts, two places.

Four options were on the table. Three are refused on evidence the map already produced:

- **A capability grade** (`local-only` / `local+remote`) is the conflation **#343 §2 already broke**: *"Remote does not imply isolated — an Actions job hosting every Lane separates them exactly as weakly as a laptop does."* An ordinal grade re-imports it, and #349 loses the vocabulary it was handed.
- **Declare primitives, derive host support** contradicts **#343 §4**, which made the seam an **outcome contract**: *"the host owes properties of a returned branch, not a sequence of steps."* There are no primitives to declare — that is what "outcome contract" means. Deriving support from primitives would rebuild the procedural contract through the back door.
- **A boolean per named host** is the shape the manifest already has, and it is the trap. `parallel_capabilities` is specified as *"exactly these boolean keys"* (`wrapper-contract.md:572`) and pinned per-member in `event-schema.json`, with both the Python and shell suites asserting the key set matches `names` exactly (`test_conformance.py:970`, `test-event-conformance.sh:83`). So **every host ever added costs a flag day** — fixture change, contract bump, three simultaneous member changes — for hosts two of the three members can never implement. ACA, out of scope but explicitly wanted, would cost one on arrival.

Note the asymmetry that makes this decisive: `insight_capabilities` is *"at least these boolean keys"* (`:495`) and is therefore additive; `parallel_capabilities` is *"exactly"* and is not. The manifest that needs to grow is the one that cannot.

**Decision: `execution_hosts`, a list of identifiers from a closed family vocabulary, declared as a sibling of the five booleans and not one of them.**

```json
"parallel_capabilities": {
  "parallel_mode": true, "rolling_dispatch": true, "integration_backlog": true,
  "adaptive_lane_limit": true, "contribution_events": false,
  "execution_hosts": ["local", "github-actions"]
}
```

This is not an invention. It is precisely the shape `rate_card` already occupies in `insight_capabilities` — *"declared alongside `names` ... but is not one of them"* (`event-schema.json`). `PARALLEL_CAPABILITY_NAMES` (`events.py:197`) stays a closed five-tuple, every existing exactness assertion keeps passing unchanged, and the new key gets its own rule. Adding a host later is then a **vocabulary** change, not a **schema** change: additive, one member at a time, no flag day.

**The vocabulary must be closed and pinned.** A member that emits `"actions"` where the family says `"github-actions"` is drift of exactly the kind the contract already refuses for event literals (*"a drifted literal ... is a conformance failure"*). Identifiers name **placement relative to the orchestrator**, per #343 §2 — never an isolation grade, which the host declares separately and which placement does not imply.

**Two facts, two places.** *Can this member drive host H* is a fact about the distribution and belongs in the manifest. *Which host did this Run select* is a fact about the Run — one host per Run, mixing not shipped (#343 §3) — and is **not a manifest key**. That mirrors `rate_card` exactly: the capability sits in the manifest, the resolved value sits on the Event beside it. **The schema of the Run-scoped half is #355's**, and it inherits the constraint that it is Run-scoped-and-per-contribution, never a capability. **How an operator selects a host is #353's**, being an invocation surface.

## 4. What Conformance asserts — and the machinery already exists, in both directions.

The ticket framed this as the hard part: *"a fixture that asserts every member implements remote hosts would break the family; a fixture that asserts every member honestly declares what it does is the point."* Correct, and the family already built that fixture for the manifest next door.

`test_conformance.py:930` derives the Python manifest **from the package source** — *"Read from the package source rather than declared, so the manifest cannot stay optimistic after a producer is removed or stay stale after one lands."* And `test-event-conformance.sh:96-108` proves the **negative** claim the same way, grepping the port's own `lib/` to confirm a `contribution_events: false` member names no producer. Both directions of "prove your declaration against your own code" are shipped. Nothing new is needed; the pattern is extended by one key.

Conformance asserts **three** things, and they differ in kind:

1. **Shape** — language-neutral, in `event-schema.json`: every member's entry carries `execution_hosts`; it is a list; every entry is drawn from the closed vocabulary; every member's Run-start Event carries it. This is the drift catcher.
2. **Entailment** — language-neutral, over the fixture's own per-member table: `parallel_mode: false ⇔ execution_hosts == []`. Enforceable for all three members from the fixture alone, with no per-language code, exactly as the existing "whole manifest false" clause is (`test_conformance.py:986-990`).
3. **Truthfulness** — per-member, in each member's own suite, read from that member's own source. Python's is source-presence-shaped, like its four existing derivations. **shell and PowerShell get the strong form for free**: their claim is `[]`, and `[]` is entailed by `parallel_mode: false`, which is already proved. *A negative claim needs no new proof machinery* — the second dividend of #343 scoping the seam to Lane contributions.

And the sentence that keeps the family intact, which belongs in the fixture's own `unsupported` note beside the existing one:

> **Conformance pins the relationship between a declaration and its producer. It never pins the content of a declaration.** No fixture may require any member to support any host.

**One addition makes the declaration load-bearing rather than decorative.** Source-presence proves the code *exists*; it cannot prove the code *behaves*. #343 §6 gave six refusals a conformant host owes — never silently retries, never writes to the tracker, never mints identity, is not a scheduler, is not a policy engine, is not the Run's observability endpoint. Those are obligations of the **host**, not of the member (the #343 follow-up was right to keep the two declarations distinct). So they are gated by a **per-host fixture set**, and:

> **A declared identifier is a subscription to a fixture set.** Declaring `github-actions` obliges the member to pass the `github-actions` host suite.

That is the whole answer to *"how does a member prove its declaration is truthful"*: presence proves existence, the host suite proves behaviour, and a member that wants neither declares `[]` and owes nothing.

## 5. Refuse, never degrade — and the "inconsistency" #343 flagged is not one.

The #343 follow-up observed that the family *"currently does both, in different places, and that inconsistency is worth naming."* Named, and dissolved: the two answer different questions.

- **`git_loopy_assert_parallel_supported`** (`shell/lib/orchestrator.sh:1274-1302`) refuses because the **distribution** lacks the capability. No environment change fixes it; the operator must change a setting or change distribution. The message says all three: the unsupported capability, the distribution that cannot honour it, the setting to change.
- **The degrade at `loop.py:2217-2222`** fires because the **Run's source** cannot supply the input — the PRDs backend has no `parallel-safe` concept — and the fallback *does the same work with the same outcome*, so *"opting into Parallel mode never strands eligible work."*

The rule that separates them, stated once so nothing has to re-derive it:

> **Refuse when the missing thing is a property of the distribution. Degrade only when the fallback reaches the same outcome and strands nothing.**

Applied here, both halves point one way. A requested host absent from `execution_hosts` is a **distribution** property, and a local fallback is **not** outcome-equivalent: it changes the placement, the isolation grade (#343 §2), who is billed (#357 — minutes bill to the target repo's owner), and per #350 whether the toolchain is even present. So:

**Decision: refuse at preflight, at the existing site, in the existing shape** — the three-part message, the §10 preflight-failure exit code. No new doctrine, one more clause in the sentence the contract already has at `wrapper-contract.md:600`.

**Silent degradation is never acceptable here**, and for a sharper reason than "unattended Runs need loud failures": #350 made a missing toolchain a **`GateError`, never a Strike**. A silent local fallback would execute a contribution in an environment the operator did not choose and charge the difference to the **Strike** machine — #352's *"status line that lies"*, with money attached.

**On reusing `invalid_request` (#302): no, and the reason matters.** That shape is the **Continuation** boundary's envelope for a machine caller (`continuation.py:388` `CapabilityUnsupported`, `:4878`). Host selection is a **Wrapper**-contract preflight surface answering to an operator. Both refusals are shipped, and they are not competing — they belong to different contracts with different callers. Reaching for `invalid_request` would drag host selection into the Continuation contract, which is decision §1's category error arriving by a second road.

## 6. Not second-class — and the docs change is one clause, not a new phase.

Confirmed, and #343 §5 supplies the reason rather than a reassurance: there is no grade of second-classness in having no Lanes, because an Execution host is a property of a **Lane contribution** and these members have none. They are not missing a capability; they never had a contribution to place.

But the ticket's instinct — *"whether the docs should say so plainly rather than implying parity that does not exist"* — is right, and the plain statement already exists in the right place. `docs/runners.md:98-104` puts **Lanes / Rolling dispatch / Integration** in **Phase 5** and states the shell and PowerShell members *"declare `parallel_mode` unsupported in their capability manifest and refuse a Lane cap above 1 rather than accepting it and running serially."*

**Decision: `execution_hosts` is documented as a clause inside Phase 5. No Phase 6 is created.** Minting a separate "Execution hosts" phase would manufacture precisely the second-classness the ticket feared — it would read as a *second* thing these members lack, when it is the same one. One sentence earns its place beside the entailment rule in the contract:

> A member that declares `execution_hosts: []` is not missing a host. It has no **Lane contribution** to place.

**A trap worth naming, because "local" reads as "your laptop" and #350 makes that false.** Identifiers are placements *relative to the orchestrator*, so `local` means *the orchestrator's own machine, wherever that is*. #343 §3 established that where the orchestrator runs is a separate fact from where a contribution runs, and #350 kept "git-loopy running inside an Actions job" as a supported deployment. A Run deployed into Actions with worktree Lanes on that runner's disk is `execution_host: "local"` and correctly so. The manifest declares placement relative to the orchestrator; it never names a datacentre.

## 7. Version bump: the Wrapper contract, minor. Nothing else.

- **Wrapper contract: yes, 1.16 → 1.17.** `parallel_capabilities` is normative §12 text specified as *"exactly these boolean keys"*; adding a sibling and an entailment clause changes it. Same class as contract 1.5 adding `wrapper.pool.excluded` and 1.16 adding calibration records.
- **Event schema compatibility version: no — it stays `1`.** The contract is explicit at `wrapper-contract.md:438`: *"The additive Event schema has compatibility `schema_version` 1; changing the Wrapper contract does not implicitly change that version,"* and *"unknown payload fields remain additive and MUST be ignored by compatible consumers."* What moves is the **fixture revision**, 1.1 → 1.2 — the same thing that moved when Continuation added optional event types.
- **Continuation contract: no.** Nothing about Continuation changes.

That last line is the payoff of §1. Had the declaration gone into the Continuation capability manifest, a Run-execution fact would have forced a **Continuation-contract** bump, pushing every Consumer through version negotiation over a change that means nothing to them. **Placing the declaration correctly is what holds the blast radius to one contract.**

## A defect this ticket's rule exposed

Applying §5's refuse/degrade rule to the existing code found one case on the wrong side of it. `_ParallelLoop.drive` emits `wrapper.run.start` with `parallel_mode: true` and `lane_cap: N` (`loop.py:2418-2424`) and *then* branches to `_drive_serial_only` (`loop.py:2471`) when the source is not Rolling-capable. That path announces nothing. So a PRDs-backend Run invoked with `--parallel 4` is byte-identical to a serial Run under a banner claiming Lanes — the exact collapse `parallel_capabilities` exists to prevent, arriving through a *source* fact instead of a *distribution* fact.

This is not a dispatch bug (the degrade is correct and strands nothing) and it is not covered by #356, which fixed latched serial-required work *within* a Rolling source; this case never reaches a latch. Filed as an ordinary issue: [#414](https://github.com/bradcstevens/git-loopy/issues/414). It changes no decision here — it is the same reporting-not-dispatch class the map has met twice, and it is evidence for §5's rule rather than an exception to it.

## What this hands to the rest of the map

- **#355** — inherits the Run-scoped half, constrained: the selected host is an Event fact, per contribution, **never** a manifest key, on the `rate_card` template. The per-contribution stamp #343 §3 promised lands here.
- **#353** — owns how an operator *names* a host. This ticket fixed what a member *declares*; selection syntax is an invocation surface.
- **#351** — the entailment rule guarantees a member with `execution_hosts: []` has no remote branch to integrate, so Integration's remote case exists only where `parallel_mode: true`.
- **#349** — unaffected and confirmed: the member declares hosts, the **host** declares its isolation grade. A member never asserts a property it does not control.
- **#354** — unchanged. A host declares capacity, the Run decides utilization (#343 §6.1); the manifest declares *which* hosts, never *how many*.

Resolved by a `/grilling` + `/domain-modeling` session over the declaration surface, with evidence traced through both shipped capability manifests, all three members' conformance suites, and the two refusal/degrade sites in the Python and shell Orchestrators.
